## Traps discovered
- `get_or_create(..., defaults={...})` never syncs an existing row — check every place Google-verified data (name, role, avatar) should override stale DB state whenever adding a new sync point.
- CSS specificity on the poster variant: `body.route-v2 a { color: var(--poster-gold); }` (element+class) silently beats single-class component rules like `.pv-btn-primary` on `<a>` tags. House convention going forward: use two-class selectors (`.pv-btn.pv-btn-primary`) or `body.route-v2 .some-class` for anything that needs to win.
- The `config.urls_v2_root` / `public.urls_v2_supplement` split is a recurring 500-source: any new `{% url 'public:X' %}` or `redirect('public:X', ...)` added anywhere in shared templates/views needs a matching alias added to `urls_v2_supplement.py`, or the poster deploy breaks while the production deploy stays fine (making these both easy to miss and easy to ship blind).
- Patching `staff.google_auth.get_verified_google_user` in tests is required, not `core.google_auth...` directly — `staff/google_auth.py` re-exports via `from core.google_auth import *`, which binds the name at import time, so patching the source module has no effect on the re-exported caller (gives a false negative).
- `DJANGO_TLS` is deliberately still `false` — flipping it would force `SECURE_SSL_REDIRECT`/`Secure` cookies globally and break the still-live raw-IP:port (`204.168.249.99:8102`/`8105`) access paths. `CSRF_TRUSTED_ORIGINS` was the correct fix for the HTTPS-domain CSRF 403 instead.
