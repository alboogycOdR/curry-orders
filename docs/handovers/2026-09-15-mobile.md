## Traps discovered
- **`PopScope`/back-button placement**: a `PopScope` must be a genuine descendant of the `Navigator`/`Router` it's meant to gate — wrapping it around `MaterialApp.router`'s `builder` `child` (i.e. above the Router) means it is never part of the pop-propagation chain the system back button walks. It will pass `flutter analyze` and a full signed release build with **zero errors** while being completely non-functional at runtime. First shipped broken this way (commits `869392d`/`7e4fa51`), caught live by the user ("back button on the Calendar screen exits the app"), fixed by moving the `PopScope` down into `features/staff/staff_scaffold.dart` — the shared chrome every staff screen's content is actually wrapped in (commit `3acb16b`). **Going forward: any Flutter back-button/`PopScope` change in this project needs an actual widget test simulating `tester.binding.handlePopRoute()`, not just compile success, before it's trusted.**
- **XML comments forbid a literal `--` anywhere in the body**, not just as the closing `-->` — broke `AndroidManifest.xml`'s manifest merge (`SAXParseException: The string "--" is not permitted within comments`) even though `--` is used freely as a separator in this project's Python/Dart/Kotlin comments. `./gradlew assembleRelease --stacktrace` (not the `flutter build apk` wrapper's default truncated output) was needed to see the real cause.
- **`local_auth`'s Android `BiometricPrompt` needs a `FragmentActivity` host** — `MainActivity.kt` had to change from `FlutterActivity` to `FlutterFragmentActivity`.
- **Background-task "killed"/"completed" status labels can be stale/wrong** relative to the actual build outcome — a timing race between OOM-kill detection and the build's own final APK write caught this session at least 3 times (once a false "exit code 0" over an actual Gradle failure; twice a false "killed" over an actual success moments later). Only the real APK file's timestamp (`ls -la` vs current time) and/or grepping the build output for `BUILD FAILED`/`Built build` is trustworthy.
- This Windows dev machine runs low on memory (~15.8GB total, often only 2-5GB free from other concurrent apps) during `flutter build apk --release` — not a code problem; work around by killing stray `java`/Gradle-daemon processes and/or temporarily lowering `android/gradle.properties`' `org.gradle.jvmargs` Xmx, **always** reverting to the committed `-Xmx8G -XX:MaxMetaspaceSize=4G -XX:ReservedCodeCacheSize=512m -XX:+HeapDumpOnOutOfMemoryError` before committing (verify via `git diff --stat` showing clean).
- `google-services.json` is intentionally committed to git (app config, not a bearer credential) — the Firebase service-account **key** is the actual secret and stays server-side only, matching the existing release-keystore handling convention.

## Don't touch
- `mobile/android/app/google-services.json` being committed to git is deliberate, not an oversight — do not treat it as a leaked secret or move it server-side.
- `DJANGO_TLS=false` remains deliberately off (see the general handover `docs/handovers/2026-09-15.md`) — `core/http.py::absolute_media_url` works around the scheme issue this causes for media URLs specifically, rather than flipping that setting.
